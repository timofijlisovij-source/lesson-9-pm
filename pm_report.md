# 1. Бізнес-контекст

- Задача: сервіс який класифікує іриси: автоматично визначає вид рослини за вимірами.
- Яке рішення підтримує: який вид квітки перед нами, тобто яку мітку присвоїти зразку.
- Користувач результату: ботанік або застосунок, який показує користувачу назву виду.
- Яка помилка небезпечніша: versicolor і virginica легко переплутати, адже вони частково перетинаються за ознаками. Тому небезпека у впевненій помилковій відповіді замість невпевненої, але чесної.
- Головна метрика: accuracy на test (класи збалансовані: по 50 квіток кожного виду, у test по 15), а loss використовуємо як другу метрику, бо вона штрафує за впевнені помилки.

# 3. Кандидат на staging / production

Обраний run: `rf-depth3`

- Чому саме він: має найвищу accuracy (0.956, тобто 43 з 45) і найнижчий loss (0.141) серед усіх runs, до того ж це єдиний run із збереженою моделлю.
- Ключова метрика: accuracy разом із loss. Loss важливий, бо показує, що модель не просто вгадує, а впевнена в правильних відповідях.
- Baseline для порівняння: є, `logreg-baseline` (0.933 / 0.191).
- Наскільки покращення суттєве: accuracy краща на 0.022, тобто на одну квітку з 45. Loss краще на 26% (0.191 → 0.141). Покращення loss помітніше, але на малому test воно може бути випадковим.
- Trade-off: суперечності між метриками немає, rf-depth3 найкращий за обома. Проте, модель складніша за baseline: 100 дерев, навчання довше: 6.6 с проти 0.35 с. Довше навчання частково поячнюється збереженням моделі.
- Model artifact: модель лежить у папці model.
- Достатньо для відтворення: загалом так, але не вистачає залогованого коду, який є у інших моделях, а також датасету, через що drift може залишитись непоміченим.

## 4. Grafana / Prometheus

Prometheus показує метрики `mlflow_accuracy` і `mlflow_loss` для всіх 5 ранів. Кожна серія має мітки `experiment`, `run_name`, `run_id`, `model_type`. У графіку rf-depth3 одразу видно як найвищу accuracy і найнижчий loss. 

MLflow UI показує повні parameters, metrics, tags, artifacts і run ID кожного рану, а також порівняльні графіки.

Значення збігаються, accuracy, loss, run id ідентичні для всіх ранів.

Разом ці інструменти допомагають зробити повний audit trail, порівняти метрики для визначення найкращої моделі та моніторити стан зміни моделі у майбутньому, завдяки алертам у Prometheus.

Але для production-рішення ще бракує:
- метрик на реальних запитах після деплою;
- моніторингу drift вхідних даних та якості;
- алертів на деградацію якості, а не лише на падіння сервісу.

## 7. PM decision report

Рекомендація: Go to staging

Обґрунтування: rf-depth3 найкращий за обома головними метриками, має збережений artifact model і зрозумілий baseline для порівняння. 

Основні докази: accuracy 0.956 проти 0.933 у baseline, loss 0.141 проти 0.191, значення в Prometheus збігаються з MLflow. У rf-depth3 збережено повний набір файлів моделі для відтворення.

Основні ризики: перевага над baseline мінімальна на дуже малому тесті (1 квітка), не визначено rollback, owner та моніторинг після деплою. Не залоговано dataset і версію коду.

Що потрібно зробити перед production:
1. Зареєструвати модель у Model Registry, залогувати dataset і версію коду.
2. Визначити критерій переходу в staging і production, призначити owner рішення.
3. Описати rollback і налаштувати моніторинг якості та drift після деплою.
